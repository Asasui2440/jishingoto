# 結果の構造と表示

JSONを求められたときの設計契約。特定のAPIの厳密なJSON Schemaではなく、アプリ側で採用・検証するための項目設計とする。

## 結果の単位

| フィールド | 意味 |
| --- | --- |
| `schema_version` | 出力形式の版 |
| `analysis_basis` | `guidance_only` / `guidance_and_cases`。事例が実際に参照されたか |
| `input_coverage` | 見た写真IDと、写真外・マスク・画質による限界 |
| `scenario` | 想定する揺れ・情報の提供者・測定位置・階数等。不明を保持 |
| `objects` | 写真の観察と利用者の申告。安定した対象IDを付ける |
| `findings` | 対象ID、成立条件、想定される動きと影響、助言、根拠、不明点 |
| `sources` | 実際に参照した資料のID、URL、該当箇所、確認範囲 |
| `case_matches` | 採用した事例IDと一致・相違・不明な条件。なければ空配列 |
| `next_checks` | 対策の判断を変える未確認項目 |

`objects` の中でも、写真で見たことと利用者が述べたことを分ける。`findings` による推測を `objects` の観察へ書き戻さない。対策後の比較では対象IDを引き継ぎ、変更された条件だけを更新する。

## 表示と検証の要点

- 優先順位は対策を検討する順序とし、被害確率や部屋全体の安全点数に見せない。
- 写真へのマーカーを出す場合は、対象の写真IDと画像座標を保存する。複数写真を結合した表示座標とは分け、別写真への枠の誤配置を防ぐ。座標を確認できなければ枠は作らない。
- 検出対象0件、写真を閲覧できなかった状態、検索に失敗した状態を区別する。いずれも「安全」の値に変換しない。
- 参照IDの存在、事例IDと出典の対応、出典が実際に支える主張を確認する。見出しやJSON構造だけの検証では十分でない。
- 数値の転倒確率は初期仕様に含めない。将来導入するなら予測対象・条件・推定法・検証結果・適用範囲を別に定義する。

## ジシンゴトへの接続案

既存の「写真認識 → 家具の確認・修正 → 予想図」の間に、事例検索と被害シナリオ作成を接続する設計とする。これは接続案であり、このスキル案の作成によってアプリの実装が変更されるわけではない。

1. 認識結果には写真ごとの観察根拠を保持し、利用者の家具分類・固定状態の訂正を反映する。
2. 確認後の対象と条件で知識を検索し、上記の結果を作る。
3. 画面は「確認したこと」「起こり得ること」「備え」を表示し、出典と事例との相違は詳細で確認できるようにする。
4. 予想図生成には、採用した対象・シナリオ・保護する領域を渡す。生成の成功や構図の一致を、被害推測が正しい証拠にしない。

スキルは判断手順を、知識ベースは根拠となるデータを、アプリは画像処理・API・保存・表示を担当する。実装する際はアプリ側にも出典IDや条件の検証を用意する。
